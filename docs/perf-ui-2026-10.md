# UI performance campaign — October 2026

**Branch:** `perf-ui-render` (5 commits on top of `9d1ab228`)
**Verdict:** no optimization was kept. The campaign's deliverable is a measurement that
changes what is worth building: **in the workloads measured, reducing rendered chat rows
by 3.3× did not move flood duration, reconnect duration, or interaction latency**, even
though it cut browser work by 38% and DOM size by 70%. The chat render path was not the
binding cost in those scenarios — which is a scoped finding, not a proof that chat
rendering is cheap. See §10 for the validity domain.

`git diff 9d1ab228..HEAD -- src-svelte/src` is empty: the shipped application source is
byte-identical to the baseline. Everything added is benches, tests, harness scripts and
documentation.

## 3. Measurement validity, established before any claim

A **null test** — both arms byte-identical, 6 paired reps — set the noise floor:

| stage | win rate | median ratio | per-pair spread |
| --- | --- | ---: | ---: |
| flood wall time (in-page) | 3/6 | 1.004 | **0.807 – 1.205** |
| main-thread JS (CDP) | 5/6 | 0.980 | 0.870 – 1.064 |
| layout time | 3/6 | 1.018 | 0.900 – 1.112 |
| style time | 4/6 | 0.995 | 0.926 – 1.096 |
| chat DOM nodes / doc nodes / rows | 0/6 | 1.000 | exact |

Consequences that governed the rest of the campaign:

1. **Flood wall time cannot resolve anything under ~20% at 6–8 reps.** Identical builds
   produced ratios from 0.81 to 1.21 because machine load climbed mid-batch.
2. CDP stage metrics (ScriptDuration, LayoutDuration, RecalcStyleDuration, TaskDuration)
   are the browser-side evidence. `/usr/bin/time -l` counters measure the
   Playwright/Node process, **not** Chromium, which runs as a separate process; they are
   a harness stability check (~±1%) and nothing more. An earlier framing of
   instructions-retired as a browser tie-breaker is retracted.
3. Every candidate below was judged against these floors, not against a stopwatch.

## 5. Results

Two kinds of experiment are reported, and the distinction matters under a
byte-identical-output rule:

- **Candidates** — changes that could have been shipped. Each had to pass the output
  identity gate, and each is marked KEPT or REVERTED. exp24, exp27 and exp28 are
  candidates; all three gates passed with identical hashes.
- **Non-output-preserving probes** — counterfactuals that deliberately render a
  different number of rows in order to measure a ceiling. They are **not candidates**,
  they are excluded from every "identity gate passed" statement, and their ratios are
  never offered as evidence of a user-visible improvement. exp25 and the burst half of
  exp26 are probes.

Stage effect and total effect are reported separately throughout. "wall" always means
the flood's measured duration; "stage" means the browser work the change actually
touched. Ratios are only meaningful against the null-test spread in §3: a ratio inside
0.81–1.21 for wall time is reported as null-consistent, not as a difference.

### exp24 — pass the row's predecessor instead of `(index, messages)` — REVERTED

Hypothesis: `previousMessage = $derived(index > 0 ? messages[index - 1] : null)` makes
every row subscribe to the whole `messages` array, which is a fresh object each batch;
with a front-trimmed buffer all 200 rows re-run their derived chain per batch.

Change: `BufferLineRow` receives `previous: BufferLine | null` and `first: boolean`;
`ChatView` adds a `prevLine(i)` helper across all six call sites.

Equivalence gate: `src-svelte/test/unit/row-predecessor-equivalence.test.ts` — four
scenarios (tail append, front trim shifting every index, row becoming first, no-op
re-publication) reproduce the old repeated-time and repeated-nick flags exactly.
Non-vacuous: stubbing `prevLine` to return `null` fails 3 of 4.

| stage | win rate | median ratio | null test for comparison |
| --- | --- | ---: | ---: |
| flood wall time | 3/8 | 1.004 | 3/6, 1.004 |
| main-thread JS | 5/8 | 0.981 | 5/6, 0.980 |
| layout time | 6/8 | 0.989 | 3/6, 1.018 |
| style time | 4/8 | 1.000 | 4/6, 0.995 |
| DOM nodes / rows | 0/8 | 1.000 | 0/6, 1.000 |

Output identity gate: **all 16 runs identical.**

**Why it failed, proven by counting work instead of timing it.** A counter bench
(`src-svelte/e2e/bench/prodcount.bench.ts`) instrumented the production build:

| work per 2,000-message flood | baseline | with predecessor props |
| --- | ---: | ---: |
| predecessor lookups | 28,861 | 2,276 |
| message tokenizations | 2,200 | 2,200 |
| embed/metadata scans | 2,200 | 2,200 |
| date-separator checks | 2,200 | 2,200 |
| nick extractions | 2,200 | 2,200 |
| row renders | 2,200 | 2,200 |

The cascade was real and was removed — 26,585 lookups eliminated — but Svelte 5's
derived chain is lazy: a dirty `previousMessage` that recomputes to the same object
never re-dirties the render effect. Every *expensive* step already ran exactly once per
row render. The hypothesis was right about the cascade and wrong about what the cascade
was protecting.

### What a row actually costs (direct measurement, no A/B)

`tokenizeAndCodify()` measured directly in Node: **2,200 calls = 1.1 ms total**
(0.4–1.0 µs per call). Against 267 ms of ScriptDuration per round the entire tokenizer
is **0.1%**. The per-message budget is ~133 µs, of which essentially all is Svelte 5
component instantiation (≈10 signals per row) and DOM construction (~14 elements per
row) — not application logic.

Probe, not a candidate: force the retained-line clamp from 200 to 60 in `models.ts`.
60 rows at 17.4 px each is a fair stand-in for a viewport-sized virtual window
(`scrollHeight` 1044 vs 3395; only ~34 of 200 rows are actually visible).

| stage | win rate | median ratio | effect |
| --- | --- | ---: | ---: |
| rendered rows | 8/8 | 0.300 | 3.33× fewer |
| chat DOM nodes | 8/8 | 0.303 | 3.30× fewer |
| document nodes | 8/8 | 0.430 | 2.32× fewer |
| layout time | 8/8 | 0.578 | 1.73× less |
| main-thread total | 8/8 | 0.621 | 1.61× less |
| main-thread JS | 8/8 | 0.827 | 1.21× less |
| style time | 8/8 | 0.928 | 1.08× less |
| **flood wall time** | **6/8** | **0.995** | **none** |

Every browser-side stage moved 8/8, far outside the noise floor. The wall clock did not

### exp26 — is any workload render-bound? Not the ones measured.

**Reconnect burst** (`history.bench.ts`, relay resends 3,000 lines at once — the
workload that *should* be render-bound), 6 paired reps:

| stage | win rate | median ratio |
| --- | --- | ---: |
| history rows rendered | 6/6 | 0.600 |
| reload → last row visible | 5/6 | 0.969 |

Per-pair reload ratios were 0.913, 0.949, 0.962, 0.969, 0.977, 1.008 — every one inside
the null test's 0.807–1.205 wall spread, so the 0.969 median is **null-consistent**: the
honest reading is "no measurable change", not "3% faster". The row-count stage, by
contrast, was exactly 0.600 in all six pairs. 40% fewer rows, no measurable duration
change. Reload-to-last-row is ~255 ms of which most is connect, auth and buffer
discovery. Load during this batch reached 8.9 (1-min average) on two reps, which is
recorded in each arm's `meta.txt`.

This arm is a **probe**: it renders 60 rows instead of 200, so its output hash
legitimately differs (`c61a6890…` for the probe against `e9720034…` for the baseline,
stable within each arm across all six reps).

**The direct test of what sets the flood's wall clock.** `prodflood` now records every
inbound relay frame (Playwright `framereceived`, installed in the fixture's
`beforeConnect` because Playwright only reports websockets created after the listener
exists). Both windows are durations, so the Node and page clocks never have to be
reconciled:

```
[prodflood][round 0] render=787ms  netFrames=2031 netFirst=11ms netLast=820ms
[prodflood][round 1] render=759ms  netFrames=2056 netFirst=1ms  netLast=809ms
[prodflood][round 2] render=792ms  netFrames=2026 netFirst=0ms  netLast=797ms
```

The last frame arrives at 797–820 ms and the last row is on screen at 759–792 ms: the
render window and the arrival window are the same window, and the app is not backed up
behind the relay — it finishes rendering within ~30 ms of the final frame. What these
three per-round numbers support is that coincidence of windows; they are not per-batch
timestamps, so they do not prove batch-by-batch causality. A live flood's duration is set
by how fast the relay delivers — ~0.4 ms per message, one frame per message — and the
app's rendering sits entirely inside that span.

This also explains a measurement that looked like instability: the same build measured
923 ms per round early in the session and 1671 ms per round later, with no code change.
Each flood leaves 2,000 more lines in the channel and the relay delivers from a bigger
buffer more slowly. The benchmark's wall clock was partly measuring WeeChat's history.

### exp27 — `content-visibility: auto` on chat rows — REVERTED (measured regression)

The one lever that could have cut render work without changing what is rendered: the
DOM stays complete, only paint and layout of off-screen rows are skipped.

```css
.bufferline { content-visibility: auto; contain-intrinsic-size: auto 17px; }
```

| stage | win rate | median ratio |
| --- | --- | ---: |
| chat DOM nodes | 0/8 | 1.000 |
| document nodes | 0/8 | 1.000 |
| rendered rows | 0/8 | 1.000 |
| layout count | 4/8 | 1.000 |
| layout time | 5/8 | 0.988 |
| main-thread JS | 5/8 | 0.993 |
| flood wall time | 5/8 | 0.998 |
| **style time** | **0/8** | **1.357** |

Output identity gate: all 16 runs identical. Nothing was skipped, and style
recalculation got 36% worse in every single pair.

The specification explains it: `content-visibility` follows the applicability rules of
size containment, and size containment has no effect when the principal box is an
internal table box — a `<tr>` is `display: table-row`. Firefox
([bug 1663685](https://hg.mozilla.org/mozilla-central/rev/228f4a8ccf96b3bd724b82c7bd6ad92b4e7ba8ef))
and WebKit ([eea0af365](https://github.com/WebKit/WebKit/commit/eea0af365e1cca71d12a328eee4398d5f2db9745))
both made this explicit; the CSSWG discussion is
[csswg-drafts#7658](https://lists.w3.org/Archives/Public/public-css-archive/2022Aug/0906.html).
Chromium accepts the declaration, gains no skipping, and the containment bookkeeping
shows up as style cost.

## 7. Deliberately not attempted, with measured cost

**Virtualized (windowed) chat rows.** Its ceiling is no longer a guess: exp25 measured
what rendering 60 rows instead of 200 buys — **DOM nodes −70%, layout time −42%,
main-thread total −38%, main-thread JS −17%, and null-consistent change on flood wall
time, reconnect burst duration and interaction latency.** The remaining benefit is RAM
and CPU, not responsiveness.

This is the ceiling for **rendering 3.3× fewer rows**, measured with a blunt instrument
(a smaller retained window). It is *not* a measurement of virtualization. True
virtualization adds window management, scroll math, height estimation and history
behaviour that were never tested, and those costs are not included in the numbers above.

The cost is architectural, not incremental. It requires spacer rows whose heights are
estimates (row heights vary with wrapping), which touches the read marker, the
follow-pin loop and history loading at the top — all governed by
`docs/chat-scroll-ownership.md`, a 253-line contract with tuned constants
(`PIN_SETTLE_FRAMES=2`, `PIN_CAP_MS=400`, `FOLLOW_SETTLE_MS=250`,
`READMARKER_MAX_FAILURES=2`, `SAMPLE_ROW_LIMIT=12`, `SCROLL_BOTTOM_TOLERANCE=10`,
`VISIBLE_LINES_HEADROOM=10`) and E2E specs that assert a parked row stays within 24 px,
zero scroll writes while parked, and `diffFromBottom ≤ 4` after following. The
equivalence gate for it (`prodwalk`) is also not yet trustworthy — see §9.

**Reducing the retained window (`maxBufferLines` 200 → 60).** Same resource numbers as
virtualization for one constant. Rejected because it is not an optimization under this
session's rule: it changes what is rendered, i.e. user-visible scrollback depth, and
would increase history fetches on upward scroll. It is a product decision, and the
current formula (`min(1000, max(200, 2 × linesPerScreen + 10))`) is deliberate headroom.

**Taking rows out of the table formatting context** (`display: grid`/`block` on the
chat table, which would make `content-visibility` applicable). Output-altering: it
changes column widths and baseline alignment. Out of scope.

**DOM slimming.** The only span in a table row with no CSS rules is `.prefix-part`, and
it carries WeeChat colour classes (`part.classes`) and is referenced by three E2E specs
(`BufferLineRow.test.ts` glyph position, `MessageColors.test.ts` prefix colour,
`ChatView-copySelection.test.ts` text extraction). Merging `.compact-prefix` with
`.mention-link` or `.message-content` with `.token-group` risks the tuned baseline
alignment, text-selection and ellipsis behaviour, and would need a screenshot-hash gate
that does not exist.

**Tokenizer work.** Measured and closed: 0.1% of script time.

**Store-path micro-optimization.** `api-store-reducers.ts` already batches (one map copy
plus one lines-array copy per affected buffer per frame-aligned batch; a `lineIdsSeen`
Set replaced the O(n) id scan that was ~60% of API flood store time; `get(maxBufferLines)`
is read once per batch). `bufferProjections.ts` already uses `WeakMap` presentation
caching, row reuse keyed by id, element-wise `sameArrayByReference` comparison and
publication suppression. No measured headroom remains in either.

## 9. Remaining bottlenecks and unresolved items

**Where the time actually is.** For a 2,000-message flood the measured round is
~790–920 ms, of which the relay's delivery span is ~800 ms. Attributable app work per
round: script ~240–290 ms, layout ~60–125 ms, style ~50–60 ms. The app is busy inside
the window, not behind it.

**Unresolved — `prodwalk` is not yet a working gate.** It was written as the equivalence
gate for a windowed renderer, and it currently fails its own assertion after one step:
scrolling to `scrollTop = 0` triggers `onReachTop` history loading, which prepends
lines, shifts `scrollTop`, and the walk loop breaks on `scrollTop <= before`. It does
report useful geometry (`clientHeight` 598, `scrollHeight` 3395, 200 rows at ~17 px,
`heightDrift` 0, `peakNodes` 2813), but it must absorb or suppress the reach-top prepend
before it can certify a virtualized renderer. **This is the blocker for any future
virtualization work, and it is not solved.**

**Unresolved — no browser-side attribution tool works here.** CDP CPU profiles attach
native `(program)` / `(garbage collector)` nodes to `(root)` rather than under the JS
frame that triggered them; `analyze-cpuprofile-tree.mjs` returned 83.6% charged to
`(root)`. Browser cost has to be measured through CDP metrics and paired A/B, not
profile attribution. The tool is kept with that negative result documented in its header.

**Unresolved — benchmark drift.** `prodflood`'s wall time depends on how much history
the channel has already accumulated. Cross-batch comparisons are only valid as paired
per-rep ratios; a clean absolute baseline would need the channel reset between arms.

## 10. Validity domain — where this result does and does not hold

Everything above is scoped to:

| dimension | value in every measured run |
| --- | --- |
| Relay | gbtest, WeeChat 4.10.1, API transport on 9010 (legacy 9001 not exercised by these benches) |
| Retained window | `maxBufferLines` ≈ 200 lines |
| Viewport | 1280×720 page, chat container `clientHeight` 598 px, ~17 px per row → **~35 rows visible of 200 rendered** |
| Message composition | plain text flood from the IRC control channel — no images, no plugin embeds, minimal colour/formatting |
| Hardware | Apple M1 Pro, 8 cores, 16 GB, Playwright Chromium, production build |
| Workloads | 2,000-message live flood; 3,000-line reconnect burst; six `prodreact` interaction scenarios |
| Machine load | 1.7–8.9 (1-min average) recorded per arm; never idle |

**Not measured, and able to invert the conclusion:**

- **Scroll-heavy behaviour** — `onReachTop` history loading, fast flick scrolling,
  jump-to-search, read-marker navigation. `prodwalk`, the bench written for exactly this,
  does not work yet (§9). This is the single largest blind spot.
- **Large retained windows** — a client configured for 1,000 retained lines rather than
  200 would put far more rows in the DOM, and the render path could become binding.
- **Much larger viewports** — a 4K display renders far more of the retained window, so
  the ratio of rendered to visible rows (the thing a virtualizer attacks) shrinks.
- **Low-end hardware or CPU throttling** — an M1 Pro is not the constraint device.
- **Heavily formatted rows** — embeds, plugin output, long wrapped messages, code blocks
  with many tokens. The flood was plain text, which is the cheapest possible row.
- **Long sessions** — GC pressure and detached-node accumulation over hours were not
  measured.
- **The legacy transport** — these benches use the API relay only.

**What would change the conclusion.** A workload where the app is genuinely behind the
pipe: a relay that delivers faster than the app can render, a retained window much larger
than 200 rows, or a scroll-heavy interaction. Under the contract measured here — WeeChat
4.10.1 API relay, ~200 retained lines, ~35 visible rows, plain-text flood on an M1 Pro —
no such workload was found, and three independent measurements agree.
